## Evolución Arquitectónica: Modelo Basado en RUT

Inicialmente, el sistema web intentó utilizar el campo `ven_mail` del vendedor como puente para unificar la cartera entre empresas. Sin embargo, el análisis empírico demostró que esto era un **riesgo crítico de seguridad** debido a inconsistencias históricas en los correos (correos genéricos o compartidos).

Siguiendo el diseño de la aplicación nativa Android, la API (`get_clientes.php`) fue refactorizada para implementar un **Modelo Basado en RUT**:

1. **Aislamiento Seguro:** El servidor recibe el `vendedor_id` y la `empresa`. Consulta **únicamente** la base de datos de esa empresa (ej: `autotec_ecom.tbl_clientes`) para extraer los RUTs de los clientes asignados a ese vendedor.
2. **Puente por RUT (Cross-Company):** Con la lista de RUTs extraída, el servidor consulta la tabla maestra de deudas (`bd_automarco.tbl_cobranza`) utilizando exclusivamente `c.clirut IN (...)`.

**Resultado:** El vendedor ve automáticamente las deudas de todas las empresas para **sus** clientes, pero está matemáticamente imposibilitado de ver clientes de otros vendedores o cruzar datos por errores en la tabla de empleados.
